Choices made in step 1 that the design doc did not specify. Newest decisions go at the bottom.

## Tooling
- **uv installed via a throwaway venv.** The machine had no uv and Python 3.10; uv fetched Python 3.12 itself. `.python-version` pins 3.12 and `requires-python` is `>=3.12,<3.13`.
- **Versions** were taken from what `uv add` resolved on 2026-10-13 and are locked in `backend/uv.lock`; `pyproject.toml` uses `>=` lower bounds of those versions.
- **`httpx2`, not `httpx`,** is the dev dependency for FastAPI's `TestClient`: Starlette 1.8 emits a deprecation warning when `httpx` is used.
- **hatchling** is the build backend; `pytest` also sets `pythonpath = ["."]` because the editable-install `.pth` was not picked up in this environment.
- **Ruff** rules: E, F, I, UP, B; line length 100.
- `.claude/` is git-ignored (local tooling config).

## Domain
- **Store enum** is `coles | woolworths`. "Aldi by data only" is interpreted as: one enum line plus seed rows, no schema change (the DB column has no CHECK on store).
- **`price` is the current shelf price.** When `on_special` is true it is the special price; no separate "was" price is stored.
- **`unit_price`** is a computed field rounded to 4 dp (half up): per 100 for `g`/`ml`, per item for `each`.
- **Floats are rejected** for `price` and `pack_size` (validator), so seed JSON stores them as strings.
- `special_end_date` is only allowed when `on_special` is true.
- `data_source` is `Literal["seeded"]` as asked; widening it is a one-line change later.
- `brand_label` allows only `house_brand | branded`. "On special" is a separate flag, as the doc labels it separately.
- **Quality bands:** house brand and branded = `standard`; premium house lines ("Coles Finest", "Woolworths Gold") = `premium`; a few staples (rice, pasta, canned tomatoes, baked beans) have a `budget` house brand so tier-difference flags can be tested.

## Schema (db/migrations/001_init.sql)
- `runs.id` is `uuid` default `gen_random_uuid()` (v4, 122 random bits).
- Extra columns, each commented as inferred in the SQL: `runs.created_at/finished_at/stop_reason`, split `tokens_in/tokens_out`, `run_steps.seq/attempt/error`, `dish_cache.dish_key/model/created_at`, `usage_counters` layout.
- `run_status` values: queued, running, completed, stopped, failed. "stopped" = orchestrator thresholds, "failed" = errors or budget exhaustion.
- `usage_counters` is one row per `(day, scope, scope_key)` with scope `global | visitor | ip`; the day-stop flag lives on the global row; `day` is the Pacific-time date.
- `price_catalogue.unit_price` is a **generated column**, so it cannot disagree with price and pack size.
- Primary key of `price_catalogue` is `(store, product_id)`; product IDs are `col-`/`wol-` + slug + `-01` house brand, `-02` branded, `-03` premium.
- RLS enabled on all five tables with no policies. The migration was parsed with `pglast` but **not executed** against a real Postgres.
- ~~`dish_cache` keyed on dish name only~~ superseded in step 1b (now keyed on dish and avoid).

## Seed
- **103 ingredients, 346 products**, every ingredient has 1-3 candidates per store. Dates are relative to an anchor (see step 1b); tests use 2026-10-12 (Monday).
- **Generated once by a throwaway script** (not committed); the JSON is the source of truth and is edited directly from now on.
- Loader is a module, `grocery_planner.tools.seed_sql`, not a loose script, so it reuses the model and can be tested. Output is idempotent (`ON CONFLICT ... DO UPDATE`) in one transaction.
- The generated SQL file is git-ignored; the JSON is the committed source.

## Price lookup
- **Matching:** the lowercased, trimmed query must appear as a whole-word phrase in the product name or any search term. Whole-word so "egg" does not hit "eggplant". Blank query matches nothing.
- **Ordering:** results are sorted by `unit_price` then `product_id` before `limit` is applied, so truncation is deterministic and keeps the cheapest. `limit <= 0` returns `[]`.
- **`PostgresPriceSource`** fetches the store's rows and reuses the same Python matcher, so the two sources cannot drift apart. It opens one connection per call; there is no pool at demo scale.
- **`packs_needed`** accepts `Decimal` or `int`, raises `UnitMismatchError` (a `ValueError`) on unit mismatch and `ValueError` for non-positive quantities. No kg-to-g conversion (the doc says there is no conversion tool).
- **`pack_size_within_tolerance`** measures the gap relative to the *needed* size, inclusive at exactly the tolerance. Default tolerance is `Decimal("0.15")`.

## Step 1b

Added the `tzdata` dependency so this works in containers without a system tz database.

A special with no end date stays active. **`specials_ending_within(products, as_of, days)`** returns active specials whose end date is 0 to `days` days after `as_of`, inclusive.

- **Brand filter.** `PriceSource.search(term, store, limit, brand=None)`. Brand is compared case-insensitively on the trimmed value, with exact equality (not substring), and applied before ranking and `limit` in both sources.

Helper: `make_dish_cache_key(dish_name, avoid)` in `domain/dish_cache.py`, returning `(dish_key, avoid_key)`. The SQL notes that rows are only written after the ingredient agent's output passes schema validation.
- **README** setup now uses `brew install uv`, `uv sync`, `uv run pytest`.
- **Known limitation:** `PostgresPriceSource` filters in Python after fetching all rows for a store. Acceptable at ~350 rows; a live source would search server-side.

## Step 2 (planner tools)
- **`Store.ALDI` added to the enum** (no seed rows). The N-store test needed a third real `Store`, and this is the one-line change the earlier decision anticipated. Seed and lookup tests that looped over `Store` now name Coles and Woolworths explicitly. Searching Aldi returns `[]`.
- **`PricedItem`** requires every product field (id, name, brand, size, price, unit price, packs, total cost, timestamp, source) for exact, equivalent and substitute rows, and none for `not_found`. `special_end_date` is the exception: it stays null for matched products that are not on special. Substitute rows keep their product and cost so they can be shown, but are never used in maths. No floats for money.
- **`PlannerConfig`** values are `Decimal` (so threshold comparisons are exact) with inclusive ranges; out-of-range raises `ValidationError`. JSON floats such as `0.08` are accepted and converted via their decimal text.
- **Item universe.** The items in a comparison are the distinct `item_id`s across the rows for the given stores. A store with no row for an item counts as missing it, the same as `not_found`. Rows for other stores are ignored. Two rows for the same item and store raise `ValueError`.
- **Coverage pct** is a `Decimal` fraction (0.9 = 90%). With zero items, `should_stop` stops with the reason "no items to compare".
- **Stop rule** compares strictly: `share > stop_not_found_pct` or a per-store matched-pct rule (replaced in step 2b by the comparability rule). Exactly at a threshold does not stop. All reasons are returned, not just the first.
- **Ties for cheapest store** go to the first store in the `stores` argument. In `best_split`, an item that costs the same at the cheapest single store and elsewhere stays with the cheapest single store, so a tie never creates an extra trip.
- **`what_if_split`** raises `ValueError` if an assigned item is not a common item (it is outside the basket being compared), not usable at its assigned store, or the store is not in `stores`. It may return negative savings if the assignment is worse than the best single store. The returned assignment covers every common item.
- **`per_item_savings`** `saving` = most expensive store's cost minus cheapest store's cost. `tier_gap_flag` is true if the picks differ in `brand_label` or `match_tier`. `special_flag` looks only at the cheapest pick and uses `specials_ending_within(..., as_of, 7)`, so a special ending exactly 7 days out counts and one that has already ended does not. `specials_ending_within` and `special_active` are now generic over anything with `on_special` and `special_end_date`.
- **`rule_verdict` order of checks:** split first (split savings >= threshold), then one_store (gap >= threshold), else no_meaningful_difference. This is equivalent to the doc's three conditions, which are mutually exclusive. Threshold is based on the cheapest single-store total on common items. Raises `ValueError` with fewer than two stores or no common items (the orchestrator is expected to have stopped the run first).
- **Verdict contents:** the `split` assignment lists every common item, including those that stay at the cheapest store. `store` is set only for `one_store`. `item_savings` is attached for the agent to explain from.
- **Money display:** `format_money` rounds half up to cents with thousands separators; nothing else rounds.
- **Test fixtures** (`tests/helpers.py`) build rows from the seed through `search` and `packs_needed` (one pack each). Large-gap and threshold scenarios are constructed by scaling or overriding the seed price (`factor` / `price`), because seed prices differ by only a few percent between stores.

## Step 2b
- **Comparability replaces the per-store stop rule.** `should_stop` no longer looks at any single store's matched share. It stops when `common items / total items < stop_comparable_pct`, where common = usable at every store. The not-found rule is unchanged. Both use strict comparisons, so exactly at a threshold does not stop. A store with low coverage no longer stops a run if enough items are comparable; the design doc's "any store has fewer than 50% matched" row is superseded by this.
- **Config field renamed** `stop_store_matched_pct` -> `stop_comparable_pct` (default 0.50, range 0.40 to 0.80, unchanged).
- **`Coverage` gained `common_items`** (ids usable at every store). Per-store `matched` and `pct` stay in the result for the UI but are not a stop rule.
- **Reason text:** `"no comparable items: only 0 of 10 items are usable at every store (0% < 50%)"`; when some but too few are comparable it starts `"too few comparable items: only 4 of 10 ..."`.
- **`rule_verdict` still raises on zero common items.** This is now an invariant: with `stop_comparable_pct` at least 0.40, `should_stop` stops any run with no common items before the verdict is reached. A comment says so.
- **`ACTIVE_STORES`** (`coles`, `woolworths`) lives in `grocery_planner/config.py`. Code must use it instead of iterating the `Store` enum, which can include stores without seed data (Aldi). Nothing in `grocery_planner/` iterated the enum; the tests that did now use `ACTIVE_STORES`. A test asserts every active store has seed products and that Aldi is neither active nor seeded, so adding Aldi to `ACTIVE_STORES` before it has seed rows fails the build.

## Step 3 (Supabase)
- **Check 0 (stop-rule denominators):** the code was right and a test name was wrong. Per-store `pct` and the comparability share both divide by all distinct item ids, and common items are a subset of every store's matched items, so a store below `stop_comparable_pct` always forces a stop. The old test "low single-store coverage alone does not stop" used a store at 60% (above 50%), so it never exercised a low store. It is replaced by a parametrised test over 0-10 missing items that asserts the implication (store below threshold means stop) and the shared denominator.
- **Migration runner** (`grocery_planner.db.migrate`): applies every pending file in one transaction (all or nothing), under an advisory lock so two runners cannot collide. Applied files are recorded in `schema_migrations` (filename, applied_at), which has RLS enabled with no policies like the other tables. Changing an already-applied file is not detected (no checksums); add a new migration instead.
- **Seed command** (`grocery_planner.db.seed`): one transaction, upsert on `(store, product_id)`. It never deletes, so a product removed from the JSON stays in the table until removed by hand.
- **Connections:** `SUPABASE_DB_URL` is read from the environment, falling back to `backend/.env` via python-dotenv (existing variables win). Connections use `prepare_threshold=None` so they also work through Supabase's transaction pooler. The URL is never printed. The configured URL here is the direct connection (port 5432).
- **`PostgresPriceSource`** uses a `psycopg_pool.ConnectionPool` (min 1, max 4) and has `close()`. Still fetches a store's rows and matches in Python (known limitation unchanged).
- **Integration tests** are marked `integration` and auto-skipped when no database URL is available (`tests/conftest.py`). They seed the real database with today's anchor (the same state the daily seed produces) and compare 24 terms x 5 brand filters x 2 limits x 2 stores against the file source. The RLS test checks every `public` table, so it also covers `schema_migrations`.
- **Latency** (direct connection from the dev machine, 50 calls, warm pool): median 27 ms, p95 32 ms, max 39 ms. About 60 searches per run is therefore under 2 s, so no per-run snapshot is proposed yet. Re-measure from the real host, since that number is dominated by network round trips.
- **Design doc synced** (see git diff): Gemini 2.5 to 3.5 Flash-Lite and the deprecation item ticked; one threshold for all verdicts, with the agent following the code's verdict unless it states an override reason; dish cache keyed on dish plus normalised avoid and written only after schema validation; comparability stop rule replaces the per-store rule (`stop_comparable_pct`); seeded specials relative to an anchor.
- The doc's decision rule now says "meet" (not "exceed") the threshold, matching the code.

## Step 4 (model layer)
- **SDK findings.** `google-genai` 2.30.1. Google's docs now lead with a newer Interactions API; this layer uses the long-standing `client.models.generate_content`, which is still in the SDK and has everything needed. Structured output: `response_mime_type="application/json"` plus `response_json_schema=Model.model_json_schema()`, and we validate with Pydantic ourselves. Function calling: `FunctionDeclaration(parameters_json_schema=...)`, `AutomaticFunctionCallingConfig(disable=True)`, calls read from `response.function_calls`, results sent back as `Part.from_function_response`. Usage: `usage_metadata.prompt_token_count`, `candidates_token_count`, and `thoughts_token_count` for thinking. Thinking: 3.5 Flash-Lite supports `thinking_level` (minimal, low, medium, high) and defaults to minimal; the lowest level is `minimal`. Docs say thinking tokens are billed with output tokens and count toward `max_output_tokens`.
- **Tools and a schema in one request** works on `gemini-3.1-flash-lite` (the live smoke test does exactly that). Docs do not state it explicitly; reports say it fails on 2.5 models.
- **Gemini 3 thought signatures:** during the tool loop the model's own turn is appended to the history unchanged before the tool results.
- **Sync, not async.** Agents run in a background task per run, one request at a time, so the interface is synchronous.
- **Interface.** `LLMClient` has `generate` and `generate_with_tools`; no google types leak out of `grocery_planner/llm/`. `GeminiClient.generate_with_tools` also takes an optional `temperature` (default 0.1), which the protocol omits as the spec's signature did. `LLMResult` is a frozen dataclass.
- **`attempts` equals `usage.requests`**: total requests sent for the call (first tries, retries, repairs, tool rounds). It is kept as a separate field because the spec asked for both.
- **Output tokens exclude thinking tokens** (`thinking_tokens` is separate), so `output + thinking` is the billed output.
- **Model id** from `GEMINI_MODEL`, default `gemini-3.5-flash-lite`. **Thinking level** defaults to `minimal`; the constructor takes any level, or `None` to leave the model default.
- **Retries.** "3 attempts total, backoff 1s, 2s, 4s" is inconsistent (3 attempts have 2 gaps), so I implemented 3 attempts with delays of 1s then 2s plus up to 25% jitter, and left 4s in the table for a fourth attempt. The design doc row was reworded to match. Each underlying request is retried independently, so a tool loop can send more than 3 requests in total. Retried: timeouts and other transport errors, any `ServerError` (5xx), and per-minute or unknown 429s. Not retried: other 4xx (raised as `LLMError`) and per-day 429s. A 429 retry does not honour Google's `retryDelay` hint (it can be 30s+); after 3 attempts it raises `QuotaExhausted` and the caller decides.
- **429 classification.** The error body is searched (lower-cased) for Google's quota ids and text: `PerDay` / "per day" / "daily" means `per_day` (checked first, since waiting seconds does not cure a daily limit), `PerMinute` / "per minute" means `per_minute`, anything else is `unknown`. The id names come from forum reports of real errors (e.g. `GenerateRequestsPerMinutePerProjectPerModel-FreeTier`), not from official docs, so the live behaviour should be re-checked the first time a real 429 is seen.
- **Schema repair** is one extra request that replays the conversation, shows the model its own bad reply, and lists the validation errors (`field: message`). It is sent without tools. An empty or blocked reply is treated as invalid output. Failure raises `SchemaValidationFailed(raw_outputs=[first, second], errors)`.
- **Tool loop.** A round is one model response that asks for tools (parallel calls in one response are one round). Unknown tool, invalid args and a `ValueError` raised by the tool are sent back to the model as `{"error": ...}`; other exceptions are bugs and propagate. When the model asks for tools more than `max_tool_rounds` times, `ToolLoopExceeded` is raised (that last request is still counted). `ToolSpec.func` is called with the validated args as keyword arguments.
- **Request accounting.** `on_request(delta)` is called once per request actually sent, including failed ones (a 429 or 5xx counts as a request; its delta has no tokens). The deltas sum to `result.usage`. If a call raises, the hook has still fired for everything sent. The budget itself is not built.
- **Timeout** is set per request (`HttpOptions(timeout=30000)` in the request config). The SDK's own retry option is not used.
- **`FakeLLMClient`** script entries: a model instance, an exception instance, or `FakeToolCalls(rounds, result)`, which runs the real tools through the same `execute_tool` helper. It counts one request per call plus one per tool round and fires `on_request`. It does not simulate retries or repair.
- **Live tests** (`-m live`) only run when `-m live` is passed (`tests/conftest.py`), and need `GEMINI_API_KEY`. `grocery_planner/env.py` now owns `.env` loading for both the database and Gemini settings.
- **Live finding: `gemini-3.5-flash-lite` returns 504 DEADLINE_EXCEEDED for every request with this key** (tried on 2026-10-14 with 30s and 60s timeouts, plain prompt, with and without a thinking level), while `gemini-3.5-flash` and `gemini-3.1-flash-lite` answer in 3 to 5s. So the smoke test was run on `gemini-3.1-flash-lite` via `GEMINI_MODEL`. The default stays `gemini-3.5-flash-lite` pending your decision. Also: a persistent 504 costs 3 x 30s plus backoff (about 90s) per request before `LLMUnavailable`, which the orchestrator should keep in mind.
- **Daily budget unverified.** The design doc now says 70% of 500 requests/day = 350 with a 15% buffer, as instructed; I could not confirm 500 RPD for 3.5 Flash-Lite from the public docs (the rate-limits page does not list per-model numbers), so the "read the limits" open item stays unticked.

## Step 4b
- **Default model is `gemini-3.1-flash-lite`** (still overridable with `GEMINI_MODEL`). The design doc's Stack, Model row and the "read the limits" open item now say 3.1 Flash-Lite, plus a Known limitations row about the 3.5 timeout.
- **Probe:** `python -m grocery_planner.llm.probe [--model X]` sends exactly one structured request and prints model, latency, request count and tokens, or the error class (with HTTP code and status) and exits 1. It uses a `GeminiClient(single_shot=True)`, a constructor flag that means one send, no retries and no schema repair (an invalid reply raises `SchemaValidationFailed` with the single raw output).
- **Timeout** is 20s per request (was 30s).
- **Attempts by failure type:** timeouts and transport errors, and any 504, get 2 attempts (one retry). Other 5xx, per-minute 429s and unknown 429s get 3 attempts. Backoff before a retry is 1s then 2s plus up to 25% jitter (the unused 4s step is gone). A persistent 504 now costs about 40s instead of 90s.
- **retryDelay on 429s.** The hint is read from `error.details[].retryDelay` (e.g. `"39s"`), falling back to "retry in 3.2s" in the message. For per-minute and unknown 429s: a hint up to 20s is waited out (plus 0 to 0.5s jitter, so the wait can be slightly over 20s) instead of the fixed backoff; a hint over 20s raises `QuotaExhausted(kind="per_minute")` at once with no retry, even if the 429 was otherwise unclassified. No hint means normal backoff. Per-day 429s are still never retried, hint or not. The hint is not checked against the day-stop logic; that stays with the guardrail layer.
- **Test impact:** attempt-count tests were split by failure type; new tests cover hint under cap, at the cap (20s is waited), over the cap, hint in the message, no hint, and single-shot. The exact-accounting scenario is unchanged (its failures are one 5xx and one hint-less per-minute 429).
- **Live result:** on 2026-10-14, after these changes, `gemini-3.5-flash-lite` answered the probe in about 1.1s, so the earlier 504s were transient (or lifted on Google's side) rather than a permanent problem with the project. The default stays 3.1 as instructed; switching back is a one-line change or an env var.

## Step 5 (ingredient agent)
- **Input caps** (`domain/request.py`): meal name 1-60 chars; mains 1-4 items of 1-60; sides 0-4 items of 1-60; people 1-12; days 1-14; avoid at most 100 chars; 1-7 meals. Whitespace is stripped and empty strings in required fields and list items are rejected. A blank or whitespace-only `avoid` becomes `None` (an empty optional field means "no avoid"). Unknown fields are rejected. The field is `sides` (the doc says "minor sides").
- **Vocabulary** (`tools/vocabulary.py`, `ingredient_vocabulary()`): one entry per distinct ingredient in the catalogue (103), found by the slug inside the product id. Name = the first search term (which is itself a valid search term, so the price agent can search by it), category and canonical unit come from the products (the build fails if stores disagree). Pantry staples are a new top-level `pantry_staples` list in the seed JSON (not a product column, so no schema change): salt, pepper, olive oil, vegetable oil, sugar, flour, cumin, paprika, curry powder. This list is my choice and easy to edit.
- **One batched call** expands every uncached (dish, avoid) pair. Identical pairs across meals (same normalised dish and avoid) are expanded once. Each main and each side is a dish. Dish ids (`d1`, `d2`, ...) are assigned per request.
- **Prompt and payload.** The system prompt (see `SYSTEM_PROMPT` in `agents/ingredient.py`) says the user message is data and that instructions inside dish names or avoid text are never followed. The user message is compact JSON: `dishes` (dish_id, dish_name, avoid) and the full `vocabulary` (name, category, unit; about 1,500 input tokens). Temperature 0.1.
- **Validation lives inside the output type**, so the model layer's single schema repair covers it: the batch type checks that exactly the requested dish ids come back; that a name found in the vocabulary (case-insensitive) is marked `in_vocabulary` and uses the canonical unit; and that `in_vocabulary: true` names exist. Out-of-vocabulary names (`in_vocabulary: false`) are allowed with any unit. Quantities must be positive. After validation, vocabulary names are rewritten to the catalogue spelling and `in_vocabulary` is set from real membership.
- **Schema detail:** the model-facing JSON schema declares quantity as a plain `number` (code still parses it to `Decimal`), and `notes` is an optional string defaulting to empty, to keep the schema simple for Gemini.
- **Cache.** `DishCacheRepo` has `get` and `put`; `InMemoryDishCache` for tests, `PostgresDishCache` (small pool) for the real table. What is stored is the per-serving `DishResult` (ingredients plus assumptions) as JSON, keyed by `make_dish_cache_key`. Rows are written only after the whole batch validates; if the repair also fails, `SchemaValidationFailed` propagates and nothing is cached. A cached row that no longer passes validation against the current vocabulary is treated as a miss and overwritten. Writes record the model id.
- **Deterministic assembly:** quantity = per-serving x people x days for each meal, summed by (lower-cased name, unit) across dishes and meals; `meals` lists the meal names in order of first use (two meals with the same name collapse to one entry); `each` items are rounded up (`ceil`) after merging; g and ml keep exact decimals. Out-of-vocabulary items get category `other`, are never pantry staples, and are not sanity-checked. The same out-of-vocabulary name in two units stays as two lines.
- **Pantry staples** are dropped from `items` unless the request asks for them, with one assumption naming what was left off (or, when included, one saying they are included). The model is told not to mention staples in its own assumptions.
- **Sanity ranges** (per serving, flag only, never an error): meat 50-400 g; produce 5-400 g; dairy 5-300 g or 10-300 ml; pantry 0.5-300 g or 1-250 ml; bakery 20-200 g; frozen 30-300 g or 30-250 ml; countable items (produce, dairy, bakery, frozen) 0.05-4 each. They live in `SANITY_RANGES`.
- **Assumptions** in the result are the model's per-dish assumptions prefixed with the dish name (de-duplicated, cached ones included) followed by the code's pantry note.
- **Output** `IngredientList`: `items` sorted by category, name, unit; `assumptions`; `usage` (requests and tokens, zero when everything was cached); `cache` (hits and misses counted in distinct dishes). Not included: a "purchasable form" per item (the design doc listed one); the vocabulary name plus quantity and unit serve that purpose, so the design doc was edited.
- **Live runs** (gemini-3.1-flash-lite, one request each, 1.9 to 3.2 s, about 1,900 input and 270 to 900 output tokens): the model respected the vocabulary and avoid text; amounts varied slightly between runs (e.g. mustard appeared in one run of the Friday dinner and not the next), which is why the dish cache also makes results stable for repeated dishes. Re-running the Friday dinner made 0 requests.
- **Design doc:** Ingredient agent job steps, output fields and rules updated; the Known limitations row now reads "3.5 Flash-Lite had a transient outage at build time; the default model is chosen by eval score (step 11)".

## Step 6 (price agent)
**Open issue for review (closed in step 6b below): the pack-size tolerance rule does not fit real shopping lists.** The design doc (and the spec) compare a product's pack size with the *needed* size and call anything beyond 15% a substitute. In the live runs this made most small or bulk items substitutes: fries (300 g need, 1 kg pack), potato (600 g, 2 kg bag), mayonnaise (60 g, 400 g jar), parmesan, brown onion, garlic. Run (a) ended with 2 of 5 items comparable and the stop rule tripped; run (b) 3 of 7. The model followed the rule correctly; the rule is the problem. Pack sizes are mostly fixed by the shop, so "close to the need" is rarely true, and the cost of waste is already in the cost basis (packs actually bought). What the tolerance seems meant to catch (step 1's edge case b, "one within 15% of the other, one beyond 15%") is a difference between the two *stores'* pack sizes (500 g vs 450 g comparable; 1000 g vs 700 g not). **Recommended change, not built:** compare the stores' chosen pack sizes with each other (and flag the gap), instead of comparing each pack with the need. Until decided, the code follows the spec.
- **My extension of the spec's rule:** when the need spans several packs, a product also counts as within tolerance if the whole packs bought overshoot the need by no more than the tolerance (`pack_comparable` in `price_lookup.py`). Without it, every multi-pack need (3.6 kg of mince in 500 g packs) would be a substitute. It is arbitrary in places (spaghetti 500 g x 3 overshoots 25% for a 1.2 kg need and is a substitute, while 450 g x 3 overshoots 12.5% and is not), which is further evidence for the recommended change above.
- **Item ids.** `IngredientItem` now has `item_id` (`i1`, `i2`, ...) assigned after sorting and after pantry staples are dropped, so ids have no gaps. The price agent, `PricedItem` rows and the planner all use it.
- **Ingredient follow-ups (part 0).** `INGREDIENT_PROMPT_VERSION = "2"` sits next to the system prompt and is part of the dish_cache key. Migration `002_dish_cache_prompt_version.sql` adds the column and makes `(dish_key, avoid_key, prompt_version)` the primary key; existing rows get version `'0'` and simply never match. `bypass_cache=True` reads nothing from and writes nothing to the cache (hits 0, misses = all dishes). Brand: `DishIngredient.brand` is a string, empty for none (kept non-nullable to keep the model-facing schema simple), converted to `None` on `IngredientItem.brand`. A brand that does not appear in the dish name text fails validation, so the model layer's repair catches invented brands. The merge key is (name, unit, brand), case-insensitive.
- **Candidates.** `find_candidates` searches the item name (and a hint, if given) at each store with `limit=5` and the item's brand, merges terms, prices each with `packs_needed`, and skips products sold in a different unit than the item. `candidate_id` is the product id, so invented ids are trivially detectable. Money goes to the model as strings.
- **`on_special` shown to the model** means the special is still active on `as_of`; `PricedItem.on_special` and `special_end_date` carry the catalogue's values.
- **Output type.** The model returns, per item, a list of picks (one per store; `store` is a string) plus `retry_terms`. `candidate_id` may be null. It is not validated beyond the schema, so structural gaps are handled in code (no schema repair is triggered for them): a missing pick is `not_found` with a `no_pick` flag, and more than two retry terms are truncated.
- **Enforcement order.** Per pick: a tier of `not_found` ignores any candidate; a tier without a candidate becomes `not_found`; a candidate id that is not in that store's list becomes `not_found` with confidence `low` (kind `invented_candidate`); exact or equivalent on an out-of-tolerance candidate becomes `substitute` (kind `tolerance`). After all rounds, per item: exact stays only if every store has a pick, all picks share one brand (case-insensitive) and all are within tolerance, otherwise every exact becomes `equivalent` (kind `exact_downgraded`); a `tier_gap` flag is added when the chosen products differ in brand label or quality band. Each downgrade is recorded in `result.downgrades` and mirrored as a flag.
- **Retry round.** Triggered per item when a store has no usable pick (not_found or substitute) and the model gave retry terms (max 2). Code searches those terms at that store only and appends new candidates to the existing list; if nothing new is found for any store, no request is made. The second call covers only the items and stores that gained candidates; picks from round 1 for other stores are kept, and a missing round-2 pick leaves the round-1 pick in place. Cross-store rules run once at the end. Never a third call.
- **`reprice(items, hints, ...)`** takes the same item objects (with their `item_id`) and a hint string per id; the hint is searched as an extra term and shown to the model; exactly one request, no retry round. Items without a hint are priced as normal.
- **Result:** `PriceAgentResult(items, usage, rounds, downgrades, flags, reasons)`; `rounds` is the number of model calls (0 for an empty list).
- **Live results** (gemini-3.1-flash-lite, fixed anchor 2026-10-12): one request per list, 2.8 to 5.4 s, 3.2k to 6.0k input and 0.8k to 1.6k output tokens; zero downgrades and zero invented ids across 22 items; the seeded edge-case list priced exactly as designed (one-sided items not_found, Bellvue exact at both, bacon special flagged as a tier gap, yoghurt 700 g a substitute, chicken special ending in 3 days). The retry round did not trigger in any live run.
- **Design doc:** Price agent flow paragraph and pack-count bullet, Ingredient agent optional brand, and the Data layer dish_cache key (prompt version) updated.

## Step 6b (pack-size tolerance compares stores)
- **Decision (closes the Step 6 open issue):** pack size never changes a match tier. The tier depends only on the product (type of food, quality band, and for `exact` the brand). Removed: the "out of tolerance -> substitute" enforcement, `within_tolerance` in the model input and prompt, `pack_comparable` and its multi-pack extension. `pack_size_within_tolerance` (step 1) is kept but no longer used by the agents.
- **What the model sees instead:** per candidate, `purchased_qty` (packs x pack size) and `leftover` (purchased minus needed), as strings with units. The prompt says leftover is shown but never credited, that pack size never decides the tier, and to prefer the lower total cost, then the smaller leftover, between equally suitable products.
- **`PricedItem`** gains `purchased_qty` and `leftover_qty` (null for `not_found`, required otherwise).
- **Cross-store check (code, after enforcement):** `pack_gap_exceeds(quantities, tolerance)` is true when the largest purchased quantity exceeds the smallest by more than the tolerance, relative to the smaller; exactly at the tolerance is not a gap. Only picks with a usable tier (exact or equivalent) count, because substitutes and not-found rows are already outside the totals. The flag (`kind="pack_gap"`, no store) carries both quantities in its message, e.g. "coles 1000 g, woolworths 1400 g". It is not a downgrade and the tolerance comes from `PlannerConfig.pack_size_tolerance`.
- **Planner:** `ItemSaving.pack_gap_flag` sits next to `tier_gap_flag` and `special_flag`, computed from the rows' purchased quantities; `per_item_savings` takes a `pack_tolerance` argument (default 15%) and `rule_verdict` passes the config's value.
- **Exact now means** the same brand at every store, with a pick at every store; pack size is irrelevant.
- **`PRICE_PROMPT_VERSION = "2"`** is a constant in `agents/price.py` and is recorded as `prompt_version` on `PriceAgentResult`.
- **Spaghetti and the edge case:** purchased quantities depend on the need, so edge case (b) is stated for specific needs: spaghetti 400 g (500 g vs 450 g, within) and yoghurt 1 kg (1000 g vs 1400 g, beyond). The same spaghetti needing 500 g is a gap, since Woolworths must buy two 450 g packs (900 g). EDGE_CASES.md and the tests say so.
- **Seed audit of `each` products.** Changed: `spring-onion` (both stores) pack_size 1 -> 6, name "... Bunch each" -> "... Bunch 6 pack"; `celery` (both stores) 1 -> 10, "... Bunch each" -> "... Bunch 10 pack" (stalks). Prices unchanged. Left as they are: broccoli, cauliflower, cucumber, cos lettuce, capsicum, avocado, lemon, lime, cabbage, garlic bread (one item per pack); parsley and coriander (a bunch is the unit; sprigs are not counted); sweetcorn cobs (4), eggs (12), rolls (6), tortillas (8), burger buns (6) (already counts). The database was re-seeded (346 upserts).
- **Live runs** used `gemini-3.5-flash-lite` (via `GEMINI_MODEL`), because `gemini-3.1-flash-lite` returned 503 "high demand" on every attempt for several minutes during this step (probe and live tests, 3 attempts each). The default is unchanged. Note this also means these live results are not directly comparable with step 6's, which used 3.1.
- **Result of the new rule on the same lists:** run (a) went from 2/5 comparable (stop) to 5/5; run (b) from 3/7 (stop) to 7/7. No stop in any run. With this model the retry round ran for the first time live (run c), the code downgraded two `exact` picks (a model claimed exact for one-sided items), and the model chose a substitute (potato hash browns for potato gems) after the retry.

## Step 7 (planner agent, model fallback)
### Model layer
- **Fallback.** `GEMINI_FALLBACK_MODEL` (default `gemini-3.5-flash-lite`) is read like `GEMINI_MODEL`; `GeminiClient(fallback_model=...)` overrides it, `None` or the same model as the primary disables it, and the single-shot probe never uses it. When the primary raises `LLMUnavailable` (timeouts, 5xx, 504 after the normal attempts) or `QuotaExhausted(kind="per_day")`, the whole call runs once more on the fallback with the normal retry rules there; if the fallback fails too, its error is raised (no third model). Per-day quota is per model, so the fallback still has its own; the result records it (`fallback_reason="per_day quota"`). Not falling back: per-minute and unknown 429s (the spec named only per-day), schema failures, other 4xx and `ToolLoopExceeded`.
- **A tool conversation restarts from scratch on the fallback**, not mid-way: thought signatures are model-specific, so the primary's history cannot be replayed. Only the answering run's tool calls and repair flag are reported; usage and request counts include everything that was sent, on both models.
- **Reporting.** `LLMResult.model` is the model that answered; `fell_back` and `fallback_reason` are new. `Usage` has a `model` field (not part of equality): each request delta passed to `on_request` carries the model that served it, and sums over both models say `"mixed"`. `PriceAgentResult` and `PlannerResult` carry `model` and `fell_back`.
- **Live observation:** during this step `gemini-3.1-flash-lite` often returned 503 "high demand" (up to three failed attempts, 10 to 20 s extra); the fallback answered several of the live calls.
- **Removed** the unused `pack_size_within_tolerance` and its tests.

### Fixtures
- `tests/fixtures/price_{a,b,c}.json` hold the step 6b price agent outputs (a list of `PricedItem` with `as_of`, the answering model and fixture name), captured live (`SAVE_PRICE_FIXTURES=1 uv run pytest -m live tests/test_price_live.py`) at the 2026-10-12 anchor. `load_price_fixture` needs no API. Scenario fixtures built from (b): `large_gap_scenario` (Coles x1.2, expect one_store Woolworths) and `split_scenario` (Woolworths x1.33 except beef mince, set $10 below Coles: Coles cheapest overall by $3.02, expect split).

### Facts computed by code (`build_facts`)
- Raises `ValueError` when there is nothing to compare (fewer than two stores or no common items), as `rule_verdict` does; the orchestrator's stop rules should prevent it.
- **Flags:** `missing` and `substitute` (per store, from the coverage), `tier_gap` and `pack_gap` (per common item), `special_ends`. A special is flagged only if the verdict depends on it: for a one_store verdict, the savings of ending-within-7-days specials at the winning store are removed from the gap; for a split, the same for items moved away from the cheapest single store; if what is left is below the threshold, those items are flagged. This is an approximation (it takes each item's saving against the dearest store as its special-driven part). A no_meaningful_difference verdict never has a special dependency.
- **Confidence** (`high`, `medium`, `low`): `low` if the comparable share is below 70% or any pick (either store) among the three biggest-saving items has low confidence; else `high` if the share is at least 90%, every common pick has high confidence, and tier-gap or pack-gap items account for no more than half of the total item savings (exactly half is allowed); else `medium`. Share = common items / all distinct items.
- **Savings** in the result is for the final recommendation: the gap to the next cheapest store for one_store, the code-recomputed split savings for a split, and 0 for no meaningful difference.
- **Summary line** is rendered from the final recommendation and code numbers, e.g. "No meaningful difference: Woolworths is $1.00 cheaper on 5 common items (threshold $8.00)."; "Shop at Woolworths: $18.42 cheaper than Coles on 7 common items (threshold $8.00)."; "Splitting the shop (1 of 7 common items bought away from Coles) saves $10.00 (threshold $8.00)."

### The call
- **Input** is compact JSON of code numbers only (money as plain strings such as "8.00"): the rule verdict, the top 10 per-item savings (with each store's pick, tier, confidence, bought quantity and flags), the best split, coverage, flags, confidence and every comparable item with its category. `PLANNER_PROMPT_VERSION = "1"` is recorded on the result.
- **Tool `what_if_split`** takes a list of `{key, store}` pairs rather than a map, because map-shaped schemas are risky for Gemini; a key is an item_id or a category (case-insensitive), an item entry beats a category entry, and unassigned items stay at the cheapest single store. It returns code totals, savings, the threshold and `meets_threshold`; every figure it returns becomes quotable. Unknown keys or stores come back to the model as errors. `max_tool_rounds = 2`.
- **Output type and enforcement** (all inside the output type, so failures use the model layer's single repair): recommendation different from the verdict needs an `override_reason`; `overridden` must equal "differs"; `override_reason` must be null when following the verdict; `special_dependency` is only allowed if code flagged a special the result depends on and `match_quality` only if some item has a tier gap, pack gap, substitute or low-confidence pick; `one_store` must name the cheapest store; a split's assignment (item or category keys) is recomputed with `what_if_split` and must meet the threshold, and may be omitted only when the verdict is itself a split; tip and recheck item ids must exist, and a recheck item must be missing, a substitute, low-confidence, tier-gap or pack-gap; every `$` amount in reasoning, tips, recheck hints and assumptions (the spec said reasoning and tips; I extended it so no invented figure appears anywhere) must equal, to the cent, a code number or a tool result. Dropping `recheck_items` when `allow_loopback` is false happens after validation.
- **Result fields from code, not the model:** the one_store store is always the cheapest store; `overridden` is recomputed; split assignment is the code expansion at item level; confidence, flags, summary line, savings and the rule verdict are code.
- **A planner failure** (two invalid answers) raises `SchemaValidationFailed`; handling it is the orchestrator's job (step 8).
- **Live results** (five scenarios, models gemini-3.1-flash-lite or the fallback): (a), (b), (c) no meaningful difference; (d) one_store Woolworths; (e) split via one `what_if_split` call. No overrides were used and no repairs were needed. Some calls took 3 to 4 requests because of 503 retries and fallbacks, not because of repairs.
- **Design doc:** Planner agent (what-if tool, code-computed confidence and summary, output checks) and Stack (model fallback).

## Step 8 (orchestrator)
- **Spec vs. earlier decisions.** The step text says "any store matches fewer than the minimum share". The implemented `should_stop` (step 2b) uses the comparability rule instead (items usable at every store), and the design doc says so; I reused it as instructed. "Clamped" parameters: `PlannerConfig` rejects out-of-range values (step 2), so a run's config arrives validated and a bad value fails at the edge (the CLI reports a validation error).
- **Migration number:** the spec called the new migration 003, which was taken; it is `004_run_records.sql`. It renames `runs.models` to `models_used` and `runs.finished_at` to `completed_at`, adds `failure_reason`, `user_message`, `fell_back`, `requests`, `estimated_requests`, `thinking_tokens`, `loopback_used`, `updated_at` (heartbeat, indexed for running runs), and for `run_steps` a required `name` (ingredient, price, planner, reprice, planner_2, stop; check-constrained), a nullable `agent` (the old CHECK is dropped), `requests`, `thinking_tokens`, `summary`, `finished_at`. `stop_reason` (kept) is for runs that STOP; `failure_reason` is for runs that FAIL. `attempt` stays and is 2 for reprice and planner_2.
- **Order of work:** the queued run row is written first (uuid4 id, request, parameters used: planner config, `as_of`, bypass flag, deadline, stores, prompt versions, estimated requests = 9). `run_plan(run_id)` reads everything it needs back from that row, so it can run in any thread or process. `Runner.submit` runs it in a background thread; `Runner.start` creates and submits (step 12 will call the same runner).
- **Stop.** After the price step (and again after a reprice), `coverage` + `should_stop` decide. A stop writes a `stop` step (output: the reasons, counts and the failed items with each store's tier, product and the price agent's own reason), sets status `stopped`, `stop_reason` (`too_many_unmatched`, `not_comparable` or `no_items`) and a user message that points at the ingredient list; the planner is not run. An empty ingredient list (everything was a pantry staple) stops before pricing with `no_items`. A stop is reported to clients as a `run_failed` event with `data.status = "stopped"` (the design doc's event list has no stopped event).
- **Loop-back.** Only the first planner runs with `allow_loopback=True`. If it returns recheck items, `loopback_used` is set, `reprice` runs on those items with their hints, results are merged (re-priced items replace their rows, flags, downgrades and reasons), the stop check runs again, and `planner_2` runs with `allow_loopback=False`. A failure inside the loop-back pass fails the run (as specified) but leaves the first planner's output stored on the run.
- **Failures** (`classify_failure`): `SchemaValidationFailed` -> `schema_validation`; `LLMUnavailable` -> `model_unavailable`; `QuotaExhausted(per_day)` -> `daily_quota` (it only reaches the orchestrator after the fallback model was tried, or when there is none); any other `QuotaExhausted` -> `rate_limited`; other `LLMError` -> `model_error`; deadline -> `timeout`; anything else -> `internal`; stale -> `stale`. Each has a fixed user message; messages of failed runs that have an ingredient list add "Your ingredient list is below...". Exception text is never shown: `run_steps.error` holds only a class name (e.g. `QuotaExhausted(per_day)`, `internal error (RuntimeError)`) because the step table is public; the full trace goes to the log.
- **Deadline** (default 180 s, `RunnerSettings`, recorded in the run's parameters): checked before every step, not after, so a step that finished keeps its output; it cannot interrupt a model call already in flight (calls are bounded by their own timeouts and retries).
- **Step records.** A step row is inserted as `running` before the agent is called and completed afterwards with output, tool calls, usage (requests, tokens, thinking), model, `fell_back`, latency and a summary line. A failed step records only the error; its requests are unknown to the orchestrator, so they are not in the step or run totals (the budget guard still sees them through `record`). Run totals (requests, tokens, `models_used` in order of first use, `fell_back`, latency) are summed when the run ends.
- **Heartbeat and stale sweep.** Every run or step write refreshes `runs.updated_at`. `Runner.sweep_stale()` fails `running` runs whose heartbeat is older than 5 minutes with `stale` (queued runs are not swept). Nothing calls it on a schedule yet.
- **Events** are derived from stored state (`events_from_state`), numbered from 1 (`seq`), append-only: `step_started`, `step_completed` (summary and model, requests, tokens, latency in `data`), `loopback` (emitted just before the `reprice` step starts; lists the item ids), `run_completed`, `run_failed`. `Runner.events(run_id, after_seq)` returns the missing ones; `follow_events` polls the store until the terminal event. Tests check that events for a run in progress are a stable prefix of the final list.
- **Budget guard.** `BudgetGuard.reserve(run_id, estimated_requests)` before the run, `record(run_id, model, requests)` for every request (wired to the model client's `on_request` through an `llm_factory(on_request)` the runner calls once per run, so failed sends and fallback requests are recorded with the model that served them), `release(run_id)` in a `finally`. `NoopBudgetGuard` does nothing. Estimate = 1 + 2 + 3 + 1 + 2 = 9.
- **CLI:** `python -m grocery_planner.cli run request.json [--as-of] [--bypass-cache] [--memory] [--seed]`; it prints from the stored run (shopping list, per-store comparison, recommendation, flags, step table). Request files may carry a `parameters` object. Examples: `backend/examples/request_1.json` (Friday dinner) and `request_2.json` (three meals, a dairy avoid, pantry staples on, savings threshold $10).
- **Small changes elsewhere:** `FakeLLMClient` now reports its model on each request; the SDK's "non-text parts" warning is silenced (we read the parts ourselves).
- **Live run** (example request 1, Supabase, `gemini-3.1-flash-lite`, `--bypass-cache`): completed in 11.3 s with 4 requests (ingredient 1, price 1, planner 2 including one `what_if_split` call), no fallback, no loop-back; rows in `runs` (1) and `run_steps` (3) confirmed; the live rows were left in the database as proof.

## Step 9 (guardrails)
- **Planner tool gating.** `run_planner` offers `what_if_split` only when `best_split` savings are at least the threshold (equivalently the verdict's `split_savings`); otherwise no split can reach it, so the tool cannot change the answer and the planner makes one plain `generate` call with `NO_TOOL_PROMPT` (the same prompt with the tool paragraph replaced by "no what-if tool is available...do not recommend a split"). Checked on the fixtures: tool offered only for the split scenario, not for a, c or the large-gap case. Live planner steps are now 1 request instead of 2. `PLANNER_PROMPT_VERSION` is "3".
- **Config** (`GuardrailConfig` in `config.py`): `daily_limit` 350 (70% of 500), `admission_limit` 298 (350 minus a 15% buffer of 52), 12 requests per minute, 30 s maximum limiter wait, 5 runs per visitor and 20 per IP per day, 20 dishes. `from_free_tier()` computes them from 500, 70% and 15%; a test pins the defaults to those numbers.
- **Counters** (`usage_counters`, migration 005): rows `(day, 'global', 'global', model)` hold `used`, `reserved`, `day_stopped` and `stop_reason` per model; visitor and IP rows `(day, 'visitor'|'ip', key, '')` hold runs started. `tokens_used`/`tokens_reserved` were renamed `used`/`reserved` (they now count requests). `runs` gains `reserved_remaining` and `reservation_day` (what is still reserved for the run, and the Pacific day it was taken on, since a run can finish after midnight). Day = the `America/Los_Angeles` date.
- **reserve** is one conditional `UPDATE ... WHERE NOT day_stopped AND used + reserved + est <= admission RETURNING` (`RESERVE_SQL`) on the PRIMARY model's row, in the same transaction that writes the run's `reserved_remaining`. If it matches nothing the cause is read afterwards: day already stopped, or `used + est > admission` (this sets the stop flag), both `day_budget`; otherwise only other runs' reservations are in the way: `busy`, a transient refusal that does not stop the day (my addition). A refused run is stored as failed with that reason and never starts.
- **record** runs after each request: it moves up to `n` from the run's remaining reservation (primary `reserved` goes down by that much, even if the request was served by the fallback, because the primary was not used) and adds `n` to the serving model's `used`. Past the estimate `used` just keeps growing. It sets the day-stop flag for the primary once `used + 3` (the smallest run) exceeds the admission limit, and for the fallback once its `used` reaches the daily limit.
- **release** returns what is left of the run's reservation to the day it was taken on and zeroes it; safe to call twice. It runs in the runner's `finally`, and the stale sweep calls it for runs it closes.
- **A new pre-send hook in the model layer.** The spec says that beyond the daily limit "the next request raises BudgetExhausted", which needs a check before sending, so `GeminiClient` takes `before_request(model)`, `fallback_allowed()` and `on_quota_exhausted(model, kind)` along with `on_request`; the runner bundles them as `ModelHooks` and the LLM factory now receives that object. `before_request` raises `BudgetExhausted(model)` when the model's `used` has reached the daily limit, or when Google has said its quota is gone for the day. `BudgetExhausted` subclasses `QuotaExhausted(per_day)`, so the client falls back to the other model on it, exactly as for a Google per-day error; if the fallback is exhausted too the run fails with `budget_exhausted` ("ran out while this plan was running"). The check is not atomic with the send, so concurrent in-flight requests can overshoot the daily limit by a few; the 150-request headroom below Google's 500 absorbs that.
- **Fallback gating.** If `fallback_allowed()` is false the client behaves as if no fallback were configured. The fallback has its own counter and the same daily limit; when its `used` reaches it, or Google returns a per-day 429 for it, its `day_stopped` flag is set and it stays off until the next Pacific day.
- **Day stop flag** lives on a model's counter row. For the primary it means no new runs (`availability()` is false; reason `day_budget` or `google_quota`); in-flight runs continue. It is set by `reserve` and `record` as above, and by `quota_exhausted(model, "per_day")`, which the client calls whenever Google returns a per-day 429 for a model, whatever our counter says.
- **availability(now)** returns `Availability(available, reason, message, reset_at_utc, reset_at_sydney, day)`; the next reset is the next midnight Pacific. The message reads "...It resets at 2026-10-15 07:00 UTC (Thu 15 Oct, 18:00 Sydney time)." The CLI refuses to start (exit 3) when unavailable and prints the counters after every run.
- **Per-minute limiter** (`llm/ratelimit.py`): a sliding 60-second window per model, default 12; a request that would have to wait longer than 30 s in total fails at once with `LLMUnavailable` (so the client's fallback logic can take over) rather than sleeping first. A real client shares one process-wide limiter; a client given an injected transport has none unless one is passed, so tests are not throttled. Every send, including retries, takes a slot, after the budget check. Single process only (known limitation).
- **Visitor and IP limits** (`admit(visitor_id, ip)`): one transaction increments the visitor counter and then the IP counter with `INSERT ... ON CONFLICT DO UPDATE ... WHERE used < limit RETURNING`; if the IP limit refuses, the visitor increment is rolled back, so a refusal costs nothing. Reasons `visitor_limit`, `ip_limit`. The IP key is `sha256(ip + salt)` where the salt is `sha256(IP_HASH_SECRET + ":" + pacific date)`, derived rather than stored, so it rotates daily and never sits next to the counters. Without `IP_HASH_SECRET` a random per-process secret is used (with a warning), which resets IP counts on restart; the API step must set it. Counter rows are never pruned yet.
- **Dish cap:** `PlanRequest` rejects more than 20 dishes (mains plus sides across meals) with "A plan can include at most 20 dishes in total ... you have N". Per-field caps are unchanged.
- **Failure reasons added:** `day_budget`, `busy`, `budget_exhausted` (with user messages); `run_steps.error` shows `BudgetUnavailable(...)` or `BudgetExhausted`.
- **Tests:** the budget tests run against both the in-memory and the Postgres implementation (same body, fixture parameter). Postgres tests use a far-future date (2099) and test model names so they never touch real counters, and clean up after themselves. 20 threads reserving at once against a 20-request admission limit: exactly 2 get in, `reserved` never exceeds the limit.
- **Live** (CLI, example 1, Supabase, two runs): 3 requests each (ingredient 1, price 1, planner 1: no tool offered); counters 3 then 6 used, 0 reserved, limits 298/350; availability true, reset 2026-10-15 07:00 UTC / 18:00 Sydney. The fallback model's counter stayed at 0.

## Step 10 (Langfuse tracing)
- **SDK:** `langfuse` 4.18 (OpenTelemetry based). A project's old trace endpoints return 410 for organisations created after 2026-09-16, so the live check read the new observations endpoint instead (trace-level tags and name are not returned by it; they are asserted at the exporter level in tests).
- **Where it hooks in:** the model layer and the orchestrator only; agents are untouched. `ModelHooks` gains `start_generation` (called right before each send, returns a handle that is ended with the output, usage or error class) and `on_tool_call`; `GeminiClient` and the fake client call them. A request that never went out (budget refusal, limiter timeout) creates no generation.
- **Interface:** `Tracer` -> `RunTrace` -> `StepTrace` -> generation handle, with `NoopTracer` (default), `LangfuseTracer` and `RecordingTracer` (tests). The runner always wraps the tracer in `SafeTracer`, which catches and logs (once per method, then at debug level) every exception at every level and falls back to no-op objects, so a tracer that raises on every call changes nothing about a run (tested with two kinds of exploding tracer). Export is the SDK's batching; at run end `flush` runs in a daemon thread and the run waits at most 5 s for it.
- **Shape:** trace `plan_run` (trace id = `create_trace_id(seed=run_id)`, deterministic), one span per step (`ingredient`, `price`, `planner`, `reprice`, `planner_2`, `stop`), one `llm_request` generation per model request (retries, repair, fallback and tool rounds each separately; metadata: attempt, kind = request | repair | tool_round, fell_back, turns, error class), `what_if_split` as a `tool` observation under the planner span. A tool span is created after the tool ran, so its duration is about zero and the real one is in its metadata (`latency_ms`). Normal run = 7 observations (trace + 3 spans + 3 generations), with the loop-back 11, with a retry and a repair 9; a test asserts the happy path is at most 12.
- **Trace attributes:** name `plan_run`; tags `[env, ingredient@2, price@2, planner@3, model:<primary>]` (versions from the run's stored parameters); the Langfuse `environment` is `APP_ENV` lower-cased (anything other than dev, eval or prod counts as dev, with a warning); metadata `as_of`, meals, dishes, the config used, `bypass_cache`. Input is the request. No visitor id or IP is ever passed to a tracer (a test scans the exported attributes). The root span and trace attributes are entered as a context (`propagate_attributes`) for the whole run, which is why the run's trace is opened and closed in the same thread.
- **Generations:** input is `{"system_prompt": "<agent>@<version>", "user": <the user payload in full>, "last_turn": <repair prompt or tool result when relevant>}`; the system prompt text is never sent. Output is the model's text (or its function calls) in full. Usage details are `input`, `output` and `thinking`.
- **Code-only work:** no spans. The runner wraps the price source in a `CountingSource` and puts `catalogue_searches` and `catalogue_candidates` (deltas for the step) in the step span's metadata, along with the step's requests, tokens, model, fell_back and would-be cost; ingredient spans carry `cache_hits`, `cache_misses`, `dishes`, `items`; planner spans carry recommendation, confidence, flags and tool-call counts. An all-cached ingredient step therefore has no generation.
- **Would-be cost:** `tracing/pricing.py` holds paid-tier prices per 1M tokens, checked 2026-10-14 against Google's pricing page (which said "last updated 2026-10-13"): `gemini-3.1-flash-lite` $0.25 input / $1.50 output, `gemini-3.5-flash-lite` $0.30 / $2.50, output including thinking tokens; no length tiers apply to these models. Each generation gets `cost_details` from the model that actually served it (so a fallback request uses the fallback's price); an unpriced model contributes nothing (logged once). The run total is summed from the per-request hook, independent of whether tracing is on, and stored in the new `runs.would_cost_usd` (migration 006); `runs.cost_usd` stays the actual charge (0). Every cost carries a note that it is hypothetical. Live example: 7,725 in / 1,362 out tokens = $0.003974.
- **Stored on the run:** `runs.langfuse_trace_id` (only when tracing is on). The URL is built on demand (`Tracer.trace_url`, via the SDK) and printed by the CLI; it is not stored.
- **Keys and region:** the project's `.env` has `LANGFUSE_HOST` twice (the cloud.langfuse.com default and the JP region host); the later one wins when loaded, which is the region the keys belong to. Remove the first line to avoid confusion. One Langfuse client exists per public key in a process (the SDK caches it), so tests use a unique key per test.
- **CLI/config:** `tracer_from_env()` returns the Langfuse tracer when both keys are set (and `LANGFUSE_ENABLED` is not false), otherwise the no-op tracer, and the CLI says "tracing is off" in that case. `APP_ENV` and `LANGFUSE_ENABLED` are in `.env.example`.
- **Live run** (example 1, `APP_ENV=dev`, `gemini-3.1-flash-lite`): trace `7dfdc00d35d3520425f130d002548c8e`, 7 observations, would cost $0.003974, stored in `runs.langfuse_trace_id`.

### Conditional verdict (`planner_math`, code only)
- `rule_verdict` runs the rule at current prices, then again with every usable common pick that is on an active special put back to its regular price (the same picks, not a re-pick). If the recommendation is the same (same kind, same store or same split) `condition` is null. Otherwise the current-price verdict is returned with `condition = {valid_until, items, fallback}`:
  - `items` are the specials that change the outcome: each is reverted on its own, and those that flip the verdict are kept; if none does alone (it takes two together), all specials are listed.
  - `valid_until` is the earliest `special_end_date` among those items. A special with no end date never stops, and if there is no date at all the verdict has no condition.
  - `fallback` is the regular-price verdict with every special reverted (kind, store, assignment, totals, gap, threshold, split savings), not only the ones listed in `items`, as specified.
- **Summary line.** One store: "Woolworths is $11.40 cheaper if you shop by Tue 20 Oct (beef mince special); after that, no meaningful difference." A split or no-meaningful-difference verdict gets the same kind of clause ("...but only while the X special lasts (to Tue 20 Oct); after that, ..."). The fallback phrases are "no meaningful difference", "shop at X ($N cheaper)" or "a split saves $N". An overridden (`match_quality`) result keeps its old suffix and no condition.
